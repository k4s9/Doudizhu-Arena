# Agent 纯算法工具：设计、性能与面试讲述

交付日期：2026-10-03。实现两个工具：`compare_hand_plans` 和 `analyze_threat`。工具自身没有模型、网络或数据库依赖；LLM 只负责决定何时调用、选择参数以及最后出牌。

## 1. 从产品问题解释设计

现有流程已经自动提供手牌、场上牌、完整叫分/行牌历史和记忆。把这些信息再次包装成取数工具，会增加往返次数。此次选择了两种取决于模型当前疑问的计算：比较具体出法，以及检验具体威胁。

工具适合承接有明确输入、可以验证、LLM 手算容易出错的组合问题。若后续发现某项分析每步都需要且足够便宜，可直接改为流程自动运行；工具调用本身不是最终目标。

## 2. 如何使用

在创建比赛页面勾选“启用出牌分析工具”。默认关闭；开关同时应用于该场比赛的所有 LLM 牌手，随机牌手不受影响。也可以通过创建比赛 API 的 `config.enable_tools: true` 开启，保存后的比赛配置会保留该值。

直接调用单个 Agent：

```python
agent = LLMAgent("player", provider, enable_tools=True)
cards = await agent.decide_play(ctx)
```

通过 `MatchRunner` 执行时，以 `MatchConfig(enable_tools=True)` 为准；它会设置传入的全部 LLM 牌手。适配器需支持 `generate_turn()`，实际模型/网关还需支持原生工具调用。工具只开放给出牌阶段。

两个算法也可以直接从 `arena.agent.tools` 导入，用 `AgentContext` 和下面的参数进行无模型调用。示例牌必须替换成当前手牌中的合法出法：

```json
{
  "actions": [
    {"cards": ["♠3", "♥3"]},
    {"cards": ["♠4", "♥4"]}
  ],
  "constraints": {"preserve_bombs": true}
}
```

`actions` 接受 1–3 项。空 `cards` 表示 Pass，仅跟牌时合法。`preserve_bombs=true` 要求原有炸弹/火箭作为完整独立牌组使用：可以直接打出整炸，但不能拆开，也不能作为四带二核心。不同候选互不影响，一个候选非法不会抹掉其他候选的结果。

`compare_hand_plans` 的每个结果包含：

| 字段 | 含义 |
| --- | --- |
| `groups` | 实际剩牌的一种完整合法分组，每张牌恰好使用一次 |
| `lower_bound` / `upper_bound` | 静态最少分组数的已证明下界 / 可实现上界 |
| `minimum_groups` | 仅在 `exact=true` 时有值 |
| `exact` / `truncated` | 是否完成最优性证明 / 是否只返回受限结果 |
| `singletons` | 返回分组中的单张，不是原手牌中的孤张统计 |
| `broken_groups` | 候选动作拆开的同点数组合或火箭，不把所有重叠顺子都当作固定结构 |

这些组数只计算候选出牌后的剩牌，不含当前这一手，也不表示实际出完所需回合或胜率。

威胁分析参数：

```json
{"event": "can_finish", "target_seat": "E"}
```

```json
{"event": "can_beat", "target_seat": "N", "cards": ["♠A", "♥A"]}
```

目标必须是另一个当前活跃玩家。给出 `cards` 时，检验能否压过这个合法自家候选；否则使用当前场上牌。`can_finish` 还要求目标一次用完全部剩牌；没有场上牌时，它检验“假设获得自由领出权，能否一手走完”。工具不判断实际轮次、是否会轮到目标或中间玩家怎么行动。

结果有三态：`possible` 表示至少找到一种可行隐藏牌分配；`ruled_out` 表示已穷尽相关合法牌型并全部排除；`unknown` 表示信息不一致、历史缺失或搜索未完成。`complete` 表示问题已有证明支持的答案，`search.exhaustive` 才表示候选遍历结束。一个证据即可证明存在，故 `possible` 可以在非穷举时 `complete=true`。

## 3. 算法亮点一：把花色组合压缩为点数问题

手牌用 15 维计数向量表示，依次对应 3 到大王。不同花色的同点数牌在牌型搜索中等价，选择一对 3 不必枚举所有花色组合。生成器按单张、对子、三条、顺子、连对、飞机及带翼、四带二、炸弹、火箭等 15 类模板生成，再调用正式 `recognize()` 复验。

生成器允许限制牌数，用于威胁工具只枚举与目标剩余张数相关的合法出牌。返回自家方案时，再从真实手牌中还原花色，避免输出自己没有的牌。

难点在于项目规则并非任意斗地主规则的合集，例如飞机带单要求不同点数的翼。算法必须遵循当前引擎，不能直接套用外部规则库。实现过程中发现原识别器可能接收飞机带翼后附加的多余牌，却不把那些牌放进 `Trick`。本次加入总张数约束并用回归案例覆盖，同时保留生成器的“输入每张牌均被识别结果包含”校验。

规则版本已升至 `duplicate-four-seat-v3-complete-airplane`。历史冻结实验需要保留旧源码，或重新准备当前版本的实验，不能静默混合比较。

## 4. 算法亮点二：可中止、仍提供可靠结果的分组搜索

先用同点数组和贪心得到一个有效完整分组，作为上界。候选生成完整时，用最大单组长度导出下界，再按分组数做迭代加深搜索。

每个递归状态都选最小的剩余点数为锚点，只尝试包含这个点数的牌组。任何完整分组都必定有一组包含锚点，因此不会漏解；同时去掉先选 A 再选 B、先选 B 再选 A 的排列重复。失败的 `(剩余计数, 剩余组数)` 状态会记忆化，剩牌能一手出完时通过哈希命中提前结束。同一次比较中，只差花色的候选复用分组结果。

这仍是组合搜索，没有宣称多项式最优解算法。关键工程处理是维护证明边界：完整排除 k 组解后才能把下界提高到 k+1；中途超限就返回现有可行分组和已经证明的下界。如果候选生成都没完成，非空剩牌只能采用保守下界 1。

默认整次比较共享 20,000 节点 / 90 ms 预算，并非每个候选单独获得一份。检查位于候选生成和递归扩展处；最终排序、输出组装也消耗少量时间，因此不是硬实时截止保证。

## 5. 算法亮点三：不枚举全部对手手牌的威胁证明

未知点数池为“整副牌 − 自己当前手牌 − 所有人已经打出的牌”。公开底牌已经属于某人的手牌或已出牌，不能再扣一次。

对手出牌只允许使用点数，不能用引擎内部花色追踪某张具体底牌是否打出。地主剩牌的必要点数下界使用：

```text
地主至少还持有的某点数 = max(该点数底牌数量 − 地主已打同点数数量, 0)
```

工具先枚举一手可能构成威胁的合法牌 P，再检查能否把它扩充为目标的完整手牌。令 U 为未知池、L 为目标必须持有的下界、R 为必须留给另一个隐藏玩家的下界、s 为目标剩余张数：

```text
H[i] = max(P[i], L[i])
要求：sum(H) <= s，H[i] + R[i] <= U[i]
并检查另一玩家容量及能否从剩余 U − H − R 中填满目标。
```

三名活跃玩家中，观察者只需分配另外两个人的牌；除必要下界外，其余牌可自由分配，因此逐点数容量与总容量检查足以判定这种扩充是否存在。每个候选只需 O(15) 的检查和构造，不需要遍历所有隐藏手牌组合。找到时返回标注为假设的点数手牌作为可验证证据。

额外剪枝来自响应长度：跟单只需考虑单张、四张炸弹或两张火箭；没有必要生成更长的飞机。早期基准暴露了枚举无关牌型浪费时间的问题，增加安全的长度上界后消除了这类开销。

Pass 可能来自策略选择，不能据此硬性删除目标能压牌的分配。模型也不能把 `possible` 解读为高概率，把 `unknown` 解读为没有威胁。

## 6. 系统难点：算法快，调用链仍需有界

执行路径为：`LLMAgent → generate_turn → 本地注册表 → 纯算法 → 原生 tool result → 模型最终动作 → 正式动作校验`。

- 注册表通过字段白名单创建本次决策的观察快照，移除对手出牌花色、赛后全员手牌等信息；只暴露两个工具的 JSON Schema。
- 每次最多两个工具调用，参数最多 4,096 字符、结果最多 8,000 字符；不允许模型自由指定搜索预算、seed、SQL 或其他牌桌。
- 原有 `retry_limit + 1` 是总模型调用上限。工具往返占用该额度，最后一次请求保留历史和工具定义，但用 `tool_choice=none` 要求最终动作。调用总期限仍由牌桌控制。
- 计算放入工作线程，线程不持有数据库或模型句柄。取消后即使有限计算尚在收尾，也不会追加结果、写日志或执行动作。
- OpenAI/Claude 共享内部 `ToolCall` / `LLMResponse`，各自转换原生协议；旧文本路径继续工作。Claude 畸形非对象工具输入在进入历史前拒绝，避免后续每次重放都在本地失败。
- `agent_tool_calls` 记录决策关联、工具版本、观察哈希、参数/结果哈希、耗时、长度、缓存及搜索信息；模型每一轮进入现有 `llm_call_logs` / `call_evidence`，有预算账本时逐次预留和结算。

算法毫秒级并不自动保证整次决策更快：按需调用通常增加一次模型往返。要分别报告算法耗时、模型等待和总延迟，不能用工具计算速度代替端到端速度。

## 7. 可复现的性能证据

原始数据：[benchmark.json](reviews/20261003-agent-tools/benchmark.json)。本机 CPython 3.12、aarch64，固定种子，19 类场景各 100 次，共 1,900 次测量；每类另有两次不计入统计的预热。计时覆盖算法调用，排除样本构建、模块导入、注册表和模型往返。

10 月 4 日再次执行相同的 1,900 个输入，并扩展基准脚本保存逐次原始观测；算法源码未改动。最新计时、复算方法与入口见[复现与性能实测](reproduction-and-performance-20261004.md)。下表保留 10 月 3 日历史测量，不与新一轮混算。

| 场景 | P95 |
| --- | ---: |
| 10 张手牌，比较 3 个出法 | 3.091 ms |
| 17 张手牌，比较 3 个出法 | 27.976 ms |
| 20 张手牌，比较 3 个出法 | 60.788 ms |
| 正常威胁场景中最高的场景 P95 | 1.140 ms |

700 次拆牌调用含随机手牌、飞机、连对、多炸弹和保炸弹约束，共 2,100 个候选：2,054 个完成最优性证明，46 个达到节点上限后返回上下界，最慢调用 62.705 ms。1,000 次正常威胁分析全部得到确定结论；200 次缺历史/零预算故障测试全部返回 `unknown`。网络连接及 DNS 尝试均为 0。

复现命令（项目根目录）：

```bash
conda run --no-capture-output -n doudizhu-arena python -I -B scripts/benchmark_agent_tools.py --output /tmp/agent-tools-benchmark.json
```

脚本保存输入哈希、源码哈希和机器信息，并检查测量期间源码未变。不同机器、负载和时间限制会影响耗时及 `exact` 比例。此结果证明本地算法为毫秒级，尚未执行同任务的真实 LLM 推理对照，也未验证真实对战胜率收益。

正确性采用小规模独立穷举 oracle，而非只断言返回 JSON：分组结果对比最少分组穷举；威胁结果对比“先分配完整隐藏手牌，再枚举出牌子集”的暴力方法。另覆盖 15 类牌型、花色等价、底牌下界、未公开信息不影响输出、预算耗尽、取消后不写入、工具禁用和原生 SDK MockTransport 往返。

10 月 3 日最终验收：后端全量 **614 项通过**，耗时 215.59 秒，离线保护记录 0 次网络连接尝试；前端 **11 项通过**，生产构建成功。测试包含真实本地工具参与的完整复式对局，模型响应由 mock 提供。[验收记录与复现命令](reviews/20261003-agent-tools/README.md)和[后端原始报告](reviews/20261003-agent-tools/backend.xml)已保存。基准涉及的五个源文件在该轮验收时逐项匹配；后续基准脚本的观测记录改动另有新运行证据。

## 8. 面试时可以直接讲的两分钟版本

> 我做的是斗地主多模型 Agent 对战平台。原先状态和历史已经自动放进上下文，所以我没有继续增加重复取数工具，而是挑了两类模型容易算错、程序又能快速验证的问题：指定出法的剩牌最少分组，以及公开信息下对手是否可能形成某种威胁。
>
> 第一个工具把花色组合压成 15 维点数计数，完整生成合法牌型，用迭代加深、锚点去重和失败状态缓存搜索分组。难点是搜索不能拖慢决策，所以我同时限制节点和时间；算不完也返回一个可行解与证明过的上下界，不把近似答案说成最优。
>
> 第二个工具没有穷举所有对手手牌，而是枚举相关合法出牌，再用点数容量和底牌下界判断能否扩充成完整手牌。这样每个候选只需检查 15 个点数，并能给出具体假设证据。对方 Pass 不代表没有大牌，信息不足也不能说没有威胁。
>
> 两个算法都不调用 LLM。本机 1,900 次离线测试中，20 张手牌比较三个方案的 P95 约 61 毫秒，正常威胁场景的最高 P95 约 1.14 毫秒。我用独立穷举 oracle 检查正确性，并把原生工具调用接进原有预算和日志。下一步要验证按需调用是否改善真实对局得分；目前没有把算法速度包装成胜率提升或端到端加速。

## 9. 常见追问

**为什么不全部自动计算？** 基础统计适合自动提供；比较哪些候选、保留哪些结构、检验哪个玩家的威胁取决于当下判断。应再与固定规则自动触发同一算法做对照，若自动方式收益相同且更便宜，就采用自动方式。

**为什么不是 MCTS？** 这里先解决可验证的组合与可行性问题，避免先引入对手策略、隐藏牌分布等额外假设。真正的策略推演需要另外评测，并非简单复用随机牌手就能获得可靠胜率。

**怎么证明没有看对手牌？** 算法只接收白名单观察；注册表先去掉反思用全员手牌和对手花色，工具参数不能传状态。测试改变被禁止的字段而保持观察不变，结果与状态哈希保持一致。

**怎么证明不会误判安全？** 只有完整搜索结束才 `ruled_out`；找到完整分配证据才 `possible`；缺数据或超预算为 `unknown`。所有结论均限定在公开信息和当前规则中。

**工具加速了多少倍？** 目前可以报告毫秒级算法分布，不能给出同任务 LLM 倍数。还应测量“关闭分析 / 固定规则触发 / 模型按需调用”三组，同模型、同局面、同费用和总时限比较得分、调用次数与端到端延迟。

**可以写进简历的表述是什么？** “实现两类纯算法 Agent 工具，通过点数状态压缩、有界分组搜索及公开信息容量约束提供可验证决策辅助；接入双供应商原生调用与预算审计，完成 1,900 次离线性能基准。”附上述本机 P95 即可；不写未经验证的胜率增长、硬实时 SLA 或真实网关全面兼容。
