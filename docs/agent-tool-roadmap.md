# P3：有用途、可对照的 Agent 工具

建议第一个实现 `list_legal_plays`（合法出牌候选），随后按实验结果决定是否增加手牌分析和经验检索。本文件是设计评估，下面的工具尚未接入模型运行链路。

| 顺序 | 工具 | 返回什么 | 能复用什么 | 需要补的工作 |
| --- | --- | --- | --- | --- |
| 1 | `list_legal_plays(limit)` | 当前局面的合法候选、牌型、主点数、是否可过牌、是否截断 | `engine/rules.py` 的 `recognize`、`can_beat`、`validate_play` | 按点数计数生成复杂牌型，去重、限额、稳定排序；首家不能过牌 |
| 2 | `analyze_hand()` | 单张、对子、炸弹、顺子候选、拆牌影响等确定性特征 | `engine/hand.py`、规则识别 | 只说明牌型事实；启发式“估计几手出完”须单独标记，不能宣称最优解 |
| 3 | `recall_experience(query, role, limit)` | 本牌手的经验条目、来源比赛、版本、匹配依据 | 本轮 `memory_versions` 和来源关联 | 先将总结拆成可追溯条目，再按角色/牌型过滤；数据量足够后再比较全文索引与向量检索 |
| 可合并到 1 | `check_play(cards)` | 是否合法、错误原因、牌型 | 现有规则反馈与动作校验 | 与已有非法后反馈功能重复较多，适合做候选工具的内部校验，单独展示价值较小 |
| 后续 | `count_public_cards()` | 公开打出牌的点数计数、未知牌池 | 公开出牌历史 | 只能返回公开信息能推导的范围；不能读取其他玩家的手牌或当前未公开底牌 |

## 第一个工具的实现边界

- 工具从执行器持有的 `AgentContext` 取状态，模型只提供 `limit` 等允许的参数，不能自行传入对手手牌、比赛 ID 或任意 SQL。
- 现有 `RandomAgent._find_beating_plays` 不枚举顺子、飞机等完整复杂牌型，不能直接包装后声称“全部合法出牌”。新候选生成器按点数计数递归生成，经正式规则复验；若只覆盖部分牌型，响应必须标明覆盖范围。
- 响应使用稳定候选 ID、完整自家牌标识、牌型和主点数，附 `truncated`。一个点数组合对应多种花色时只保留规范代表；候选顺序不能误写为胜率排序。
- 候选有效性绑定当前 `state_hash`。模型提交候选后，规则引擎仍校验持牌、跟牌、时序与状态，拒绝旧局面的候选。
- 先用进程内工具注册表和 JSON Schema。现有 OpenAI/Claude provider 的 `generate()` 返回文本，需要扩展结构化的 tool-call/result 契约；不能只在 prompt 里列函数名就称为原生工具调用。MCP 可留作后续外部工具互通需求。
- 建议试验起点：每次决策最多 2 次工具调用、最多 20 个候选、工具结果最多 4,000 字符；计算期限和总决策期限分别控制。具体数值需用复杂牌型基准校准，尚无性能承诺。
- CPU 密集的候选生成须有搜索节点上限，不能只依赖协程超时；达到上限返回受限结果。超时、参数错误、无候选都产生结构化结果，再按决策总预算重试或合法兜底。
- 记录 `decision_id`、工具名/版本、输入状态哈希、响应摘要/哈希、耗时、输出长度、是否命中上限，以及工具前后的模型调用。后续模型 token 和费用进入现有预算账本。

## 怎么验证值得加入

先冻结同一批局面，比较三组：现有规则反馈；自动把候选注入提示词；模型按需调用候选工具。后两组可区分“多了有效信息”和“模型自主决定调用工具”的效果。

模型版本、初始经验、局面、最大输出 token、总模型调用次数和总费用上限一致。工具调用占用相同决策时间预算，不能额外赠送模型重试次数。工具结果长度计入后续提示词，单列工具计算耗时与模型等待耗时。

报告首答合法率、最终合法率、重试与兜底率、工具调用率、拒绝/超时率、输入输出 token、已知费用与未知费用占额，以及总延迟的中位数和 P95。先按独立 seed 做配对比较，再对冻结配置做完整 AB 对战验证差分得分与胜率；固定局面合法率不能证明对局策略更强。

最低验收包括：首家不可过牌、复杂牌型覆盖、花色去重、不泄露隐牌、过期候选拒绝、恶意/超长参数、搜索上限、调用次数上限，以及关闭工具时现有行为不变。工具收益不足时保留实验结论，不为简历强行增加调用链复杂度。
